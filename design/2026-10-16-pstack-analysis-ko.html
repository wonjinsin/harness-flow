01 / EXECUTIVE BRIEF

한눈에 보는 결론

pstack은 Cursor 에이전트에게 “어떻게 일할 것인가”를 가르치는 엔지니어링 운영 규약입니다. 진입점인 /poteto-mode가 요청을 플레이북에 연결하고, 조사·설계·구현·실행 증명·리뷰·PR 처리에 필요한 스킬과 모델을 호출하도록 지시합니다. 일부 상태 관리와 검사 스크립트는 실제 코드이지만, 전체 흐름을 강제하는 독립 실행 엔진은 아닙니다.

판단 요약 · [INFERENCE]

실행 가능한 개발환경과 명확한 완료 조건이 있는 팀에는 강력합니다. 작은 변경에도 조사·복수 설계·재검증이 겹칠 수 있고, 승인 없이 진행하는 기본값이 강하므로 비용과 권한을 좁혀 도입하는 편이 안전합니다.

소스 사실 파일에 선언되거나 코드에 구현된 내용입니다. 실행 확인 이번 조사에서 직접 실행한 결과입니다. [INFERENCE] 구조에서 도출한 장단점이며 실측 성능·품질 보장이 아닙니다.

02 / EXECUTION MODEL

무엇이 어디서 실행되는가

① Cursor가 제공하는 기반

채팅·Task 서브에이전트·모델 선택·클라우드 실행·MCP 도구·브라우저/터미널 제어 같은 실행 능력은 호스트가 제공합니다. pstack은 이 능력을 어떻게 조합할지 지시합니다. 설치만으로 모든 외부 시스템의 접근권한이나 앱 실행환경이 생기지는 않습니다.

② pstack이 제공하는 규칙

.cursor-plugin/plugin.json이 ./skills/와 ./agents/를 등록합니다. SKILL.md는 호출 조건과 단계, 참조 문서는 리뷰 기준·프롬프트, 플레이북은 작업별 순서를 담습니다. 등록 매니페스트 ↗

③ 주 채팅이 지휘자

/poteto-mode를 받은 채팅이 플레이북·할 일·서브에이전트 생성을 소유합니다. 지휘 자체를 다시 poteto-agent에 맡기지 않습니다. 일반 작업 위임은 이 래퍼를 쓰되, how·why·swarm·interrogate 등은 각자의 에이전트 유형을 따릅니다. 위임 계약 ↗

④ 일부 절차는 실행 코드

orch는 장기 작업 상태를 파일로 저장하고, watch-pr는 GitHub 상태를 감시하며, check-plan은 계획 문서 구조를 검사합니다. 이 도구들이 LLM 판단이나 실제 앱 검증을 대신하지는 않습니다. 계획 검사 코드 ↗

중요한 경계

등록 매니페스트와 pstack 파일 트리에는 범용 도구 차단용 훅이 없습니다. “먼저 재현”, “독립 검증”, “되돌릴 수 없는 행동은 멈춤”은 주로 에이전트가 따라야 하는 규칙입니다. [INFERENCE] 보안 통제로 사용하려면 호스트 권한, 브랜치 보호, CI 같은 별도의 강제 장치가 필요합니다.

03 / REQUEST LIFECYCLE

한 요청이 처리되는 순서

  1. 모드 연결

    슬래시 메뉴에서 /poteto-mode를 붙입니다. 일반 Enter는 한 메시지에 연결하고, macOS Option+Enter 또는 Windows Alt+Enter는 매 턴 유지되는 사용자 모드로 설정하는 방식이 README에 안내돼 있습니다.

  2. 분류와 계약

    요청에 맞는 플레이북을 읽고 그 단계들을 그대로 할 일 목록에 옮깁니다. 생략하는 단계도 지우지 않고 skip: 이유를 남깁니다. 대규모 단일 작업은 figure-it-out, 상시 프로젝트는 Orchestrate로 넘어갑니다.

  3. 근거와 형태 확보

    비단순 변경에는 how, 함수 경계를 넘는 설계에는 architect가 연결됩니다. 기존 구조의 의도가 중요하면 why도 호출합니다. 관찰로 답할 수 있는 선택은 사람에게 묻기보다 실험·프로토타입으로 확인합니다.

  4. 분리된 작업 실행

    코드·판단·설명·검증 역할별 모델을 고릅니다. 쓰기 작업은 별도 출력 위치나 worktree로 격리하고, 새 수정 라운드에는 원칙적으로 새 에이전트를 사용합니다. 기존 프로세스나 미커밋 변경이 필요한 경우에만 같은 에이전트를 이어 씁니다.

  5. 진짜 결과를 검증

    컴파일 통과 대신 앱의 실제 동작·저장값·프로파일·스크린샷 등을 봅니다. 버그는 수정 전후 같은 경로를 확인하고, 숫자는 벤치마크 점검을 거칩니다. 충돌하는 설계는 다중 모델 반박 리뷰로 점검합니다.

  6. 전달과 후속 운영

    목적에 맞는 설명과 증거를 전달합니다. 코드 작업의 PR 정리, PR을 merge-ready로 만드는 Babysit, 실제 병합을 다루는 Shipping은 구분됩니다. 조사·설계 전용 요청까지 무조건 코드를 바꾸거나 PR을 여는 것으로 해석하면 안 됩니다.

트리거와 라우팅 ↗ 플레이북 계약 ↗ 모드 사용법 ↗

계획이 없다는 뜻은 아니다

별도 planning 스킬을 기본 진입점으로 두지 않을 뿐입니다. architect는 호출자 사용례→타입·시그니처→대안 설계로 시작하고, 다단계 작업에는 전용 계획 플레이북이 있습니다. 설계 승인 중단점은 기본 필수가 아니며 /architect with checkpoint처럼 명시할 때 활성화됩니다. 승인 단계 ↗

04 / COLLABORATION

비슷해 보이는 병렬 스킬의 차이

스킬무엇을 나누는가판정·산출물주의할 점
how복잡한 질문을 2~4개 조사 각도로 분리. 단순 질문은 explainer 하나.조사 결과를 explainer가 개념·흐름·위치·함정으로 설명.단순 경로도 서브에이전트 비용이 듭니다. 근거 ↗
arena같은 문제를 여러 후보가 각자 해결.3~6개 평가 기준, 교차 심판, 기본안 선택, 좋은 부분 이식, 최종 재검증.후보 전체를 읽고 합성해야 합니다. 크게 갈리면 평균내지 않고 문제를 다시 정의합니다. 근거 ↗
swarm서로 다른 범위의 커버리지, 동일 과제 경주, 혼합.미리 정한 first pass / rank all / best-of 기준에 따라 통합 보고.누락을 PASS로 세지 않습니다. SHA·방법이 빠진 결과는 한 번 재시도 후 공백으로 남깁니다. 근거 ↗
interrogate같은 diff와 의도를 서로 다른 모델이 독립 검토.Act on / Consider / Noted / Dismissed와 모델별 일치·불일치.자동 수정하지 않습니다. 다수 일치는 높은 신호이지 정확성 증명이 아닙니다. 근거 ↗

architect는 이 위에 놓인 설계 루프입니다. 먼저 how로 기반을 이해하고, arena로 적어도 두 개의 구조적으로 다른 설계를 비교합니다. 실제 호출자 사용례에서 타입과 모듈 경계를 유도하며, 구현 과정에서 같은 종류의 이탈이 반복되면 잘못된 설계를 폐기하고 다시 설계합니다. 전체 설계 루프 ↗

리뷰 다양성의 한계 · [INFERENCE]

서로 다른 모델 가족을 쓰면 단일 모델의 맹점을 줄일 가능성은 있습니다. 그러나 동일한 누락된 맥락이나 잘못된 명세를 공유하면 같은 결론으로 틀릴 수 있습니다. 리뷰 합의보다 실제 실행 증거와 반례 재현이 더 강한 근거입니다.

관문·주의. 산출물은 진단입니다. 수정은 별도 요청·흐름으로 다룹니다.

관문·주의. 체크포인트는 선행 차단 단계, 독립 작업, 공유 쓰기 상태, 최소 안전 분할의 네 항목을 포함합니다.

관문·주의. 버리는 실험입니다. 프로덕션 코드와 섞지 않으며, 시각적 선택은 스크린샷·상호작용으로 확인합니다.

관문·주의. 성공 기준은 diff 0입니다. 통과시키려고 baseline을 바꾸지 않으며, 기준 자체가 잘못되면 질문합니다.

플레이북 원문 ↗

관문·주의. 주관적 문체까지 억지 테스트로 고정하지 않습니다. pstack에 create-skill 자체가 번들된 것은 아닙니다.

플레이북 원문 ↗

관문·주의. 실제 transcript와 열어 본 파일을 확인합니다. 후보의 자기평가를 결과로 대체하지 않습니다.

플레이북 원문 ↗

관문·주의. merge-ready에서 멈춥니다. 상태 조회 요청은 check, 새 PR 생성 자체는 감시 시작 조건이 아닙니다.

관문·주의. 녹색 CI는 병합 안전성 판정이 아닙니다. 미검증 PR 위에 놓인 PR은 먼저 통과해도 기다립니다.

06 / LONG-RUN OPERATIONS

장시간 실행과 병합의 안전장치

작업 규모와 권한은 서로 다른 축

autonomous-run은 한 작업의 완료 조건을 계속 추구합니다. orchestrate는 여러 날의 작업·PR·에이전트를 상태 저장소로 운영합니다. 독립 PR의 병합 권한까지 넘기면 autopilot-full, 의존 스택을 사용자가 마지막에 병합하려면 autopilot-stack입니다. “계속해”라는 말만으로 이 차이를 지워서는 안 됩니다.

준비와 병합을 분리

babysit은 drive·background·threads-only·check 모드를 구분합니다. shipping은 별도 검증자가 낸 PASS / PASS+NOTES / FAIL을 보고 연속으로 검증된 하단 구간만 병합합니다. 감시자가 READY라고 말하는 것과 앱 동작이 검증된 것은 다릅니다.

검증 결과를 코드 버전에 연결

Orchestrate의 ledger는 PR과 head SHA를 함께 기록합니다. 새 SHA는 이전 판정을 자동으로 새 코드의 증거로 삼을 수 없습니다. Shipping은 patch-id와 변경 성격으로 기존 판정의 재사용 가능성을 따집니다. [INFERENCE] patch-id가 같다는 사실 자체가 새 기반 브랜치와의 모든 상호작용을 증명하지는 않습니다.

한 상태에 한 작성자

worker는 구현을 맡고, 스택의 rebase·retarget·merge 같은 topology 변경은 지정된 작성자에게 모읍니다. 후속 수정은 새 에이전트와 통합된 작업 지시로 시작하며, standing orders·결정 기록·현재 frontier를 대화 밖에 보존합니다.

Orchestrate ↗ Autopilot full ↗ Autopilot stack ↗ Babysit ↗ Shipping ↗

숫자는 적용 범위와 함께 읽어야 합니다

  • Babysit의 CI flake/인프라 실패: 새 build 재시도는 한 번. 같은 실패가 두 번째면 단순 flake 취급을 멈추고 로그·기반 브랜치·실제 결함을 조사합니다.
  • Orchestrate의 하위 조정자: 대략 10개 동시 child의 rolling window, 중첩 깊이 최대 3. 정해 둔 실행 시간의 약 70% 시점부터 새 spawn을 멈추고 검증 결과 통합에 집중하는 운영 지침이 있습니다. 이는 스케줄러가 하드코딩한 전역 제한이 아닙니다.
  • Orchestrate의 실패 재시도: cap/OOM은 범위 축소, 네트워크는 동일 작업, 도구 오류는 모델 변경, 알 수 없는 오류는 한 번 재시도 방식으로 구분합니다. 두 번 재시도 후에는 해당 unit을 버리고 재계획합니다.
  • Multi-phase-plan: 각 PR의 unit·live·perf 증거가 필요합니다. live 10 lanes에 더해 전체 swarm에는 별도의 gates lane, perf lane, 최소 2개의 diff/receipt 감사 lane이 요구됩니다. 검증 전체가 10명으로 끝난다는 뜻이 아닙니다.
  • Autopilot-full: 사용자 go 뒤 /loop 1h 감사. code-ready head에 전체 swarm을 실행하고, 이후 단순 rebase·충돌 수정·작은 수정은 단일 검증자, 새 행동·재설계·큰 diff는 다시 전체 swarm을 적용합니다.
자율 실행의 비용 경계 · [INFERENCE]

명확한 중단 조건이 없으면 “계속 개선”은 오래 실행되는 비용 루프로 바뀔 수 있습니다. 도입 시 완료 predicate, 병합 허가 범위, 허용 시스템, 실행·비용 상한을 별도 운영 정책으로 적는 것이 좋습니다. 문서에 없는 공통 재시도 상한이나 성능 보장 수치를 추정해서는 안 됩니다.

  1. 설치와 역할 설정. Cursor에서 /add-plugin pstack, 이어서 /setup-pstack. 추론 수준과 실제 가용 모델을 확인합니다. 전체 도구 흐름을 쓰려면 cursor-team-kit의 관련 스킬도 필요합니다.
  2. 검증 기반부터 확보. 기존 앱 구동 수단이 없다면 /create-verification-skill을 사용합니다. 생성한 지침이 실제 앱에서 증거를 남기고 cleanup 뒤에도 증거가 보존되는지 확인합니다.
  3. 작은 실제 작업으로 pilot. 목표·변경 금지 영역·검증 명령·병합 금지를 넣고 한 번 실행합니다. 전체 워크플로를 믿기 전에 결과물과 로그를 직접 확인합니다.
  4. 그다음 확장. 모델·패널 규모를 조절하고, 장기 실행은 종료 predicate와 권한 범위를 먼저 고정합니다. 승인 전 설계를 보려면 checkpoint를 명시합니다.
