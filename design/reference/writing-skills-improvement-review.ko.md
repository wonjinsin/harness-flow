# writing-skills 개선 조사: 현재 설계와 참고 프로젝트에서 가져올 부분

## 0. 문서의 성격과 결론

이 문서는 앞서 수행한 `skills/writing-skills/` 개선 조사와 참고 프로젝트 비교를 한국어로 정리한 보고서다. 별도의 영문 조사 파일을 번역한 것은 아니며, 보존된 소스와 이후 실제 생성 실험을 근거로 조사 내용을 재구성했다. 새로운 실험을 수행하거나 운영 중인 스킬을 수정한 보고서는 아니다.

실제 생성물, 전체 수치, 평가 방법, 실행 기록은 [스킬 작성 방법 비교·생성 실험 보고서](skill-authoring-comparison.ko.md)에 정리했다. 여기서는 **현재 설계에서 유지할 것과 선택적으로 개선할 것**에 집중한다.

**결론:** 지금의 writing-skills를 상위 프로젝트의 긴 문서로 교체할 근거는 없다. 로컬 버전은 이미 유형별 평가, 사용자 콘텐츠 보호, 커밋·푸시 승인 분리, 작은 런타임 문서라는 중요한 원칙을 갖추고 있다. 개선한다면 **실패 유형에 맞는 지침 형태 선택**, **참고 자료를 읽을 조건의 명료화**, **평가 기준 자체의 타당성 점검**을 짧게 보완하는 방향이 적절하다.

이 개선안은 설계 제안이다. 해당 문구를 실제 writing-skills에 적용한 전후 비교는 하지 않았으므로, 효과가 검증된 수정안으로 표현하지 않는다.

## 2. 현재 로컬 버전에서 유지할 점

### 2.1 유형에 맞는 평가를 이미 구분한다

로컬 스킬은 모든 문제를 압박 평가로 다루지 않는다.

| 스킬 유형 | 요구하는 평가 | 유지할 이유 |
| --- | --- | --- |
| 규율형 | 규칙을 어길 유인이 있는 압박 상황에서 행동 확인 | 규칙을 외우는 것과 실제로 지키는 것을 구분 |
| 기법형 | 일반 적용과 변형·경계 사례 | 기본 절차와 환경 변화에 대한 적용을 함께 확인 |
| 패턴형 | 적용해야 하는 사례와 비슷하지만 적용하면 안 되는 반례 | 과도한 적용과 적용 누락을 함께 확인 |
| 참조형 | 검색, 적용, 자료가 지원하지 않는 인접 질문 | 사실을 찾는 능력뿐 아니라 정확한 사용과 한계 노출을 확인 |

특히 **참조형은 인위적인 압박을 받지 않아도 평가가 필요하다**는 구분이 명확하다. 이 원칙을 압박 평가 중심의 설명으로 되돌릴 이유가 없다.

### 2.2 실패 관찰과 최소 수정의 연결이 있다

새 스킬은 스킬 없는 기준선으로, 기존 스킬 수정은 수정 전 버전으로 실패를 확인한다. 기준선이 이미 성공하면 제안한 지침의 필요성이 입증되지 않은 것으로 본다.

사례마다 RED → GREEN을 순차적으로 진행하고, 모든 사례를 통과한 뒤 전체 회귀 평가를 수행한다. 이 흐름을 다시 도입할 필요는 없으며, 개선안은 기존 흐름 안에서 표현해야 한다.

### 2.3 사용자 콘텐츠와 게시 권한을 보호한다

RED 이전에 편집했다면 현재 작업에서 에이전트가 만든 변경 중 기준선 복원에 필요한 것만 되돌리도록 한다. 기존 사용자 콘텐츠를 삭제하거나 되돌리지 않는다.

검증 완료와 저장소 게시도 분리한다. **커밋에는 명시적 승인, 푸시에는 별도의 명시적 승인**이 필요하며, 커밋 승인이 푸시 승인을 뜻하지 않는다. 평가에 성공했다는 이유로 원격 부작용을 만들어서는 안 된다.

### 2.4 메타데이터와 본문의 역할이 명확하다

로컬 frontmatter 규칙은 다음과 같다.

- `name`: 소문자·숫자·하이픈, 최대 **64자**, 디렉터리 이름과 일치.
- `description`: 최대 **1024자**, `Use when...`으로 시작하며 관찰 가능한 호출 조건만 설명.
- 기능 설명과 실행 절차는 본문에 배치.

이는 로컬 정책이다. 다른 프로젝트의 설명 문구가 같은 접두사로 시작하지 않는다는 이유만으로 그 프로젝트의 스킬을 잘못된 형식으로 채점해서는 안 된다. 이후 실험에서도 mattpocock의 설명 형식 차이를 로컬 스타일 차이로 분리했다.

### 2.5 작은 런타임 문서와 재사용 범위를 지킨다

원칙·라우팅·짧은 예제는 본문에 두고, 큰 참고 자료와 재사용 도구는 필요할 때 읽는 보조 파일로 분리한다. 본문과 보조 파일에 같은 규칙을 반복하지 않으며, 본문은 **500줄보다 충분히 짧게** 유지한다.

일회성 해결담, 비공개 스키마, 테이블 이름, 저장소 고유 사실은 재사용 스킬에 넣지 않는다. 그런 사실은 프로젝트 문서에 두고, 스킬은 이를 찾아 적용하는 재사용 가능한 절차를 가르칠 수 있다.

## 3. 선택적으로 개선할 부분

### 3.1 실패 유형과 수정 형태를 더 직접적으로 연결한다

**추천 우선순위: 높음.** superpowers의 `Match the Form to the Failure`는 이미 있는 “가장 작은 지침으로 수정” 원칙을 구체적으로 실행하는 데 도움이 된다.

| 관찰된 실패 | 우선 고려할 지침 형태 | 피할 대응 |
| --- | --- | --- |
| 압박 때문에 알고 있는 규칙을 어김 | 실제 위반에 대응하는 금지 규칙과 관찰된 합리화 대응 | 실제 압박 상황과 무관한 모호한 권고만 추가 |
| 출력 구성이 잘못됨 | 출력의 구성 요소와 순서를 명시하는 긍정형 절차 | “장황하게 쓰지 마라” 같은 금지 목록만 추가 |
| 이미 만드는 출력에서 필수 요소 누락 | 해당 템플릿 안의 필수 항목·필드 | 템플릿과 떨어진 곳에 산문 경고만 추가 |
| 조건에 따라 행동이 달라져야 함 | 관찰 가능한 조건에 연결된 분기 | 무조건적인 규칙을 쓴 뒤 예외 단서를 계속 덧붙임 |

로컬 본문에 짧은 선택 규칙을 두거나 기존 평가 보조 자료에 연결하는 정도가 적절하다. 상위 프로젝트의 설명 전체를 복사할 필요는 없다.

**근거와 한계:** 실제 생성 과정에서 harness-flow는 유효 근거 선택을, superpowers는 면제 처리 순서를 명확히 하여 관찰된 실패를 해결했다. 이는 특정 결함에 맞춘 지침 수정의 유용성을 보여 준다. 그러나 위 표를 로컬 작성 스킬에 추가하면 작성 성능이 향상된다는 인과 효과까지 검증한 것은 아니다.

### 3.2 참고 자료를 언제 읽는지 더 명확하게 한다

**추천 우선순위: 중간.** mattpocock은 참조를 단순한 링크가 아니라 **대상과 읽을 조건을 함께 전달하는 문장**으로 다룬다. 필요한 자료가 있어도 참조 조건이 약하면 에이전트가 읽지 않을 수 있으므로, 본문으로 복사하기 전에 참조 문구를 개선한다.

현재 로컬 스킬은 이미 상세 자료 분리와 필요 시 로딩을 요구한다. 따라서 새로운 구조를 만들기보다, 각 참조가 적용되는 분기를 분명히 하는 편집 기준으로 사용하면 된다. 모든 경로에서 필요한 내용은 본문에 유지하고, 일부 경로에서만 필요한 상세 설명을 분리한다.

같은 개념의 정의·규칙·주의사항은 함께 둔다. 문서를 줄이기 위해 주의사항을 멀리 보내거나, 파일 수를 늘리는 것 자체를 개선으로 취급하지 않는다.

### 3.3 구조·선택·과정·행동 평가를 구분해 보고한다

**추천 우선순위: 높음.** ECC의 생성 도구, 준수 관찰, 별도 보유 스킬 관리에서 가져올 핵심은 기능 전체가 아니라 **서로 다른 검증이 다른 보장을 한다는 구분**이다.

| 평가 층위 | 알 수 있는 것 | 그것만으로 알 수 없는 것 |
| --- | --- | --- |
| 구조 검사 | 이름·YAML·경로·링크 등의 형식 유효성 | 에이전트가 올바르게 행동하는지 |
| 선택 평가 | 주어진 요청에서 적절한 스킬을 고르는지 | 실제 호스트가 자동 로딩하는지, 선택 후 과제를 해결하는지 |
| 과정 관찰 | 기준선·수정·재평가가 실제로 실행됐는지 | 그 과정이 다른 방법보다 우수한 결과를 만드는지 |
| 결과 평가 | 주어진 사례에서 기대 행동·출력이 나오는지 | 평가하지 않은 운영 환경 전체에서도 안전한지 |

로컬 지침은 이미 “문서 인용이 아니라 행동을 검증하라”고 요구한다. 이를 대체하지 말고 근거 보고에서 각 층위를 혼동하지 않도록 짧게 보완하는 것이 적절하다.

### 3.4 실패 판정 전에 과제와 채점기를 확인한다

**추천 우선순위: 높음.** 로컬 보조 지침은 이미 표시된 응답을 직접 읽고 인용 예제로 인한 오탐을 확인하라고 한다. 여기에 **요구사항과 정답의 모호성**도 같은 타당성 점검 대상이라는 점을 명시할 수 있다.

실제 실험에서는 다음 문제가 드러났다.

- OMC의 `r-latest` 결과는 실행 경로가 없는 `runtime PASS`를 충분한 근거로 볼 것인지에 달려 있었다. 보수적으로 보류한 해석도 타당했다.
- 원본 절차의 `i-pressure` 결과는 롤백·복구 기록 `z2`를 가설 근거로 포함할 수 있는지에 달려 있었다. 원본 설명이 그 해석을 허용했다.
- 브라우저 재실행 채점기는 서로 다른 JavaScript 실행 영역의 객체를 엄격 비교하여, 올바른 JSON을 실패로 판정했다. 생성물이 아니라 채점기를 수정해야 했다.

따라서 실패한 응답과 정답 기준을 함께 검토하고, 모호성을 발견하면 원본 결과를 보존한 상태에서 해석 차이를 설명한다. 성적이 좋아지도록 생성물을 사후 수정하거나 불리한 응답을 갈아 끼워서는 안 된다.

이 원칙은 실패를 무시하자는 뜻이 아니다. **명확한 요구사항 위반과 평가 자체의 결함을 구분하자**는 뜻이다.

### 3.5 반복 평가와 대조군은 질문에 맞게 선택한다

**추천 우선순위: 중간.** 로컬 보조 지침은 이미 비결정적 행동에 여러 새 컨텍스트 표본을 요구하고, 문구 비교 시 기준선·동일 과제·변동성 확인을 안내한다. superpowers의 반복 평가 지침은 구체적인 참고점이지만, 이번 실험의 **사례별 5회**를 모든 스킬의 보편적인 최소 횟수로 고정할 근거는 없다.

일반적인 스킬 수정에서는 기존의 미사용·수정 전 기준선이 출발점이다. 반면 **작성 방법 자체를 비교**하려면 원본 절차를 그대로 제공한 조건과 전용 작성 스킬 없이 작성한 조건도 유용하다. 그래야 단순히 과제 지식을 추가한 효과와 메타 작성 방법의 효과를 혼동하지 않는다.

모든 일상 편집에 이번 실험의 전체 장치를 강제하지 않는다. 반복 수, 대조군, 사례 범위는 답하려는 질문과 실제로 관찰된 불확실성에 맞춰 정한다.

### 3.6 원래 실행과 대체 실행의 검증 범위를 명시한다

**추천 우선순위: 중간.** gstack은 성공한 실제 작업의 출처, 실행 코드, 저장된 입력, 테스트, 설치 전 준비 영역을 연결한다. 실행형 스킬에는 참고할 가치가 있지만, 일반 지침형 스킬에 설치 수명주기까지 가져올 필요는 없다.

이번 실험의 실제 Chromium 어댑터는 생성 CLI와 파서를 검증했다. 하지만 gstack의 원래 데몬 인증·설치·자동 발견을 검증한 것은 아니다. 마찬가지로 메타데이터 선택 프롬프트는 실제 호스트의 자동 스킬 로딩과 다르다.

보고서에는 **무엇을 실제로 실행했고 무엇을 대체했으며, 무엇이 검증되지 않았는지**를 가까이 적는다. 런타임이 다른데도 같은 명칭을 쓴다는 이유로 검증 결과를 그대로 옮기지 않는다.

## 4. 그대로 가져오지 않을 부분

### 4.1 프로젝트별 학습 지식을 일반 스킬에 넣는 정책

ECC·OMC의 이력·세션 추출은 유용하지만, 프로젝트별 발견을 보존하는 목적과 harness-flow의 재사용 스킬 범위는 다르다. 비공개 스키마나 저장소 고유 사실을 전역 스킬에 저장하는 방향으로 범위를 넓히지 않는다.

“이 내용을 스킬로 만들 것인가, 프로젝트 문서에 둘 것인가”라는 판단은 참고하되, 저장 위치와 재사용 경계는 로컬 정책을 유지한다.

### 4.2 작성·감사·설치·게시의 일괄 통합

보유 스킬 감사, 동작 관찰, 설치 준비, 실제 설치, Git 커밋, 푸시는 같은 작업이 아니다. 이들을 writing-skills 본문 하나에 합치면 필요한 실행 경로와 권한 경계가 흐려진다.

특히 gstack의 “commit skill”을 Git 커밋과 같은 뜻으로 해석하지 않는다. 각 프로젝트의 원래 단계가 무엇을 변경하는지 확인하고, 로컬의 커밋·푸시 개별 승인 규칙을 유지한다.

### 4.3 문서 분량이나 강한 표현을 품질 지표로 쓰는 방식

긴 체크리스트, 많은 금지 문구, 많은 평가 호출은 그 자체로 우수성의 근거가 아니다. 필요한 조건을 빠뜨리지 않으면서 관찰된 실패를 해결하는지가 중요하다.

반대로 짧다는 이유만으로 좋은 것도 아니다. 이번에 harness-flow 생성물이 짧고 평가를 통과했다는 결과를 다른 모든 스킬과 과제에 일반화하지 않는다.

### 4.4 모든 스킬을 규율형처럼 평가하는 방식

기법·패턴·참조형 스킬을 무조건 합리화 저항과 압박 평가로 다루지 않는다. 현재 로컬의 유형별 평가 구분을 유지하며, 참조형에는 검색·적용·지원 범위 밖 질문을 사용한다.

## 5. 실제 생성 실험이 이번 권고를 뒷받침하는 범위

이후 수행한 실험에서는 공통 지침형 스킬 12개와 실행형 스킬 2개를 생성했다. 공통 분리 평가 400회와 메타데이터 선택 평가 120회를 수행했으며, 실행형 스킬은 작성된 테스트 15개, 독립 파서 사례 10개, 실제 브라우저를 통한 CLI 두 개를 검증했다.

주요 수치와 원본 응답은 [전체 비교 보고서](skill-authoring-comparison.ko.md)와 [결과 요약](skill-authoring-benchmark/results/summary.json)을 기준으로 한다. 여기서는 다음 해석만 가져온다.

- **작은 로컬 핵심을 유지할 이유가 있다.** harness-flow는 이번 과제에서 가장 짧은 공통 생성물을 만들면서 측정된 결과를 유지했다.
- **방법 전체의 우위는 입증되지 않았다.** 전용 작성 스킬 없는 대조군도 모든 엄격 평가를 통과했다.
- **명목상 점수 차이를 그대로 순위로 읽으면 안 된다.** OMC와 원본 절차 조건의 차이는 타당한 대안 해석이 있는 두 사례에 집중됐고, 이를 모든 조건에서 동일하게 제외하면 절차를 제공한 조건은 모두 통과했다.
- **평가 과정의 관찰은 유용하다.** harness-flow와 superpowers는 실제로 발견한 실패에 맞춰 지침을 수정했다. 다만 수정 횟수가 많다는 이유로 최종 생성물이 더 좋다고 할 수는 없다.

공통 과제는 두 개, 작성은 방법별 한 번이다. 풍부한 원본 정책과 명확한 출력 스키마가 제공됐으며, 일부 작성자는 라우팅 때문에 로컬 지침에도 노출됐다. 사용자 에이전트 평가는 도구 없는 단일 턴이므로 실제 다단계 운영 행동과 안전한 배포까지 입증하지 않는다.

## 6. 이후 수정한다면 확인할 성공 기준

다음은 구현 승인이나 이미 수행한 검증이 아니라, 제안한 변경을 실제로 적용할 경우 사용할 확인 기준이다.

1. **실패 형태에 맞는 수정:** 출력 형태 오류·누락·조건부 오류·압박 위반에 같은 금지문을 반복하지 않고 적합한 지침을 선택하는지 확인한다.
2. **참조 조건의 정확성:** 해당 분기에서는 필요한 보조 자료를 읽고, 관련 없는 분기에서는 불필요하게 읽지 않는지 확인한다.
3. **평가 근거의 구분:** 형식 통과, 선택 성공, 과정 준수, 결과 정확성을 서로 다른 항목으로 보고하는지 확인한다.
4. **모호한 정답의 처리:** 타당한 대안 해석이 있는 경우 원본 결과를 보존하면서 모호성을 설명하고, 명백한 실패까지 면제하지 않는지 확인한다.
5. **기존 안전 경계 보존:** 기존 사용자 콘텐츠 보호, 참조형 평가, 커밋·푸시 개별 승인, 프로젝트 사실의 저장 위치가 바뀌지 않는지 확인한다.
6. **분량과 중복 억제:** 새 내용을 추가하기 전에 기존 문구를 다듬고, 본문과 보조 파일에 같은 규칙을 중복하지 않는지 확인한다.

실제 편집은 관찰된 실패를 기준으로 시작해야 한다. 제안이 그럴듯하다는 이유만으로 추가 문구를 모두 넣지 않는다.
